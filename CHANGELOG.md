## Failure mode / hot take

The removed experiment (merged classify+draft) didn't fail because the LLM got dumber when asked to do two things at once — its reply *quality* was essentially identical to the final pipeline (4.97 vs 4.94). It failed because the **escalation rule itself is a compound condition** ("flag if this is a refund/fraud/discount/unauthorized-charge situation, **or** if the KB doesn't clearly cover the topic") and, sharing a single pass with the drafting task, the model quietly simplified that compound rule down to just its second half — "not grounded in the KB → escalate" — which fires on *any* unlisted topic, including a completely harmless feature request. The dedicated single-purpose classifier, asked to do nothing else, preserved the full rule and got it right on the identical ticket.

**The lesson**: when an agent has to apply a policy with real conditional logic (an AND/OR, an exception clause, a threshold), don't bundle that decision into a call that's also busy doing something else. The something-else doesn't have to be complex to cause this — "write a helpful reply" is not a hard task, but it was apparently enough competing objective to make the policy check regress to a simpler heuristic. Verification structurally can't fix this on its own: a verifier checking "is this escalation flag consistent with the content" would have caught it only if it re-derived the correct rule from scratch, which is really just re-running a dedicated classifier anyway. The actual fix was giving the compound decision its own undivided call in the first place — and once T05 also showed a verifier catching a genuine policy overreach (an agent trying to promise the refund outcome, not just explain it), the two lessons point the same way: **the fewer things a single call is responsible for getting right, the more of its actual logic survives.**

**Second, harder lesson (from Iteration 4, added after a second independent run contradicted the first)**: separating concerns made the error *rare*, not zero. The dedicated classifier still misfires on T04 about 1 time in 10, and — this is the part worth internalizing — a single evaluation run cannot tell the difference between "this design is reliable" and "I got a lucky draw." My first full run reported a clean 1.00/1.00 and would have shipped that number as the headline result if a second run hadn't happened to disagree. The fix I reached for first, self-consistency majority voting, is the textbook answer and it barely moved the needle (9/10 with or without it) — throwing more sampling at a low-probability, poorly-understood failure mode is not automatically a fix, and it's easy to convince yourself it worked from a single small trial in either direction. **The practical takeaway for building reliable agents: treat any single eval run's precision/recall as an anecdote until you've repeat-sampled the specific cases your pipeline got wrong, and when a residual error rate can't be cheaply eliminated, engineer the system so that error is safe (over-escalating to a human) rather than chasing the last few percent of determinism out of an inherently stochastic classifier.**

**Third lesson (from Iterations 5-6, after actually trying to fix the residual error instead of just documenting it)**: my first fix attempt (confidence-aware escalation) was a plausible-sounding hypothesis that turned out to target the wrong failure shape entirely, and I only found that out by re-running the exact same measurement protocol against the "fix" — a pure null result, honestly reported rather than reframed as a partial win. The fix that actually mattered came from a completely different direction: not "make one component more careful," but noticing that the *same ambiguous rule text* had been copy-pasted into two prompts (classifier and verifier) that each get sampled independently, so either one could reintroduce a bug I thought I'd already fixed by patching the other. **The generalizable insight: when a policy has any real conditional logic, check whether you've stated it in more than one prompt — duplicated authority over the same ambiguous judgment call is a distinct failure mode from "the model is sometimes wrong," and no amount of hardening one copy of the rule protects you from the other copy independently getting it wrong. Grep your own prompts for duplicated policy logic before reaching for a fancier sampling or confidence-scoring fix.**

**Fourth lesson, the one that matters most (from Iteration 7)**: every measurement in this document, up through the "Final (after Iteration 6)" row, was computed on replies where up to 76% of them were literally malformed JSON blobs instead of text — and the composite quality score never moved after fixing it. I found this not through evaluation, but by finally building something a human would actually look at (the reviewer dashboard) and seeing raw `{"reply": ...}` where a message should have been. The LLM judge I built specifically to be more rigorous than trusting a single run — the same judge behind every number in this table — read straight through the malformed wrapper and scored the content inside it, because I never asked it to check whether the output was actually usable, only whether it was accurate. **An LLM-as-judge and a human-facing view of the same output validate genuinely different things, and a defect can live entirely in the gap between them for as long as nobody looks at the second one.** The specific, transferable rule: never tell a model to self-format as JSON in the prompt text *and* pass `--json-schema` for the same shape — pick one, and if you must debug which, remove the prompt-text instruction and let the schema do the structuring alone. The broader rule: schema-conformant is not the same claim as content-correct, and an evaluation rubric only checks what you explicitly wrote into it — it will not notice the failure mode you didn't think to ask about, no matter how many times you run it.

**Fifth lesson, and the most humbling (from Iteration 8)**: building the dashboard didn't fix my blind spot, it relocated it. I looked at the exact same screenshots that surfaced Iteration 7's bug and did not independently notice the citation leak or the missing greeting/sign-off — a human reviewer did, from those same screenshots, immediately after I'd declared the output "genuinely clean." Two lessons stack here: first, a human-facing review surface is only as good as the scrutiny actually applied to it — I had the right artifact and still needed someone else's eyes on it to find the next defect one level down; second, fixing an under-specified instruction ("respond as ONLY a JSON object") by making it vaguer ("write only the reply, separately list citations") traded one failure mode for two smaller, more specific ones (citations leaking into the text anyway; "no preamble" over-applied to strip legitimate structure) — the fix for an over-constrained prompt is a more *precisely* specified one, not a looser one. Both required going back and being explicit about what "separate output" and "no preamble" actually meant, then re-validating with the same rigor as the original bug, not just trusting that a plausible-sounding instruction change had worked.
