# Support Ticket Triage & Reply-Drafting Agent

micro1 Agentic Workflows Hackathon submission.

## Who has this problem

A 1-3 person support desk at a small SaaS company (modeled here as **Loopwise**, a fictional project-tracking tool — see `data/kb/`). They handle a daily mix of billing questions, bug reports, refund requests, and how-to questions, and every reply has to be checked against product docs, a refund policy, and known bugs before it goes out.

## What bottleneck makes it worth solving

Doing this by hand means re-reading the same FAQ and policy docs for every ticket, and it's easy to either:
- state a policy detail wrong or invent one (a customer says "your policy says refunds are available anytime" — is that true? the agent has to go check), or
- miss that a ticket needs escalation. A refund request, a chargeback threat, or a discount ask can *sound* like a normal question but requires a human with actual authority to act on it. Getting this wrong either annoys customers with slow, inconsistent answers, or creates real liability (an agent promising a refund it can't authorize).

## What I built

A small pipeline of `claude -p` (Claude Code headless CLI) calls, each with a narrow, read-only tool allowlist:

1. **Classifier** — categorizes the ticket and flags whether it needs human approval (refund request, fraud/chargeback/legal threat, discretionary exception, or a topic the knowledge base doesn't clearly cover). Has read access to `data/kb/` to check KB coverage before deciding.
2. **Drafter** — writes the reply, grounded in `data/kb/` (Read/Grep/Glob only — never Bash, never write access). Every factual claim must cite a specific KB file/section. Never allowed to promise or execute a refund/discount itself.
3. **Verifier** — independently re-checks the draft against the KB: are the citations real, is anything invented, is the escalation flag actually correct given the ticket and draft. If it fails, the pipeline sends one redraft request back to the drafter with the specific problem; if it still fails, the ticket is force-escalated.
4. **Routing** — nothing is ever sent automatically. Every ticket lands in `outputs/agent/ready/` (verified, low-risk — a human can send with a quick skim) or `outputs/agent/needs_review/` (a human must review and act — refunds, threats, or anything ungrounded). This is the human-approval checkpoint the hackathon's ground rules require for any consequential action; the pipeline only ever writes JSON files, it never sends anything itself.

**Baseline**: a single `claude -p` call per ticket, no tools, no KB, no classification — "write a helpful reply" — representing how a team might use an LLM today without building anything around it.

**Evaluation**: the same 12 synthetic tickets, the same LLM-judge rubric (`agents/judge_prompt.md`, scoring grounding accuracy / policy compliance / tone, 0-5 each), for both baseline and agent. Escalation correctness is scored deterministically against hand-labeled gold tickets (`data/tickets/eval_set.json`), not by the judge. Full results in [`outputs/eval_results.md`](outputs/eval_results.md).

See [`CHANGELOG.md`](CHANGELOG.md) for how this pipeline evolved, including one experiment I tried and removed.

## What existed before this hackathon vs. what I built

Everything in this repository — the classifier/drafter/verifier prompts, the synthetic Loopwise knowledge base and ticket set, the orchestration scripts, and the evaluation/reliability-check harness — was built during this hackathon. The only pre-existing components used are the Claude Code CLI itself (Anthropic's product, invoked via `claude -p`) and the Python standard library; no other code, template, or dataset was reused from elsewhere.

## Ground rules compliance

- All data is synthetic (a fictional company, fictional tickets) — no real customer data.
- Every KB-reading agent call runs with `--tools "Read,Grep,Glob"` and `--permission-mode bypassPermissions` — the tool allowlist itself makes any write/send/execute action impossible, so bypassing the interactive prompt is safe here (see `src/claude_cli.py`).
- No ticket is ever auto-resolved or auto-sent; the pipeline's only output is JSON files, routed into a "ready" or "needs human review" folder.
- No credentials are stored in this repo; the pipeline authenticates however the local Claude Code CLI is already logged in.

## Reviewer dashboard

`outputs/agent/ready/` and `outputs/agent/needs_review/` are the real human-approval checkpoint, but raw JSON files aren't what the intended user (a support lead) would actually want to look at. `python3 src/build_dashboard.py` generates `outputs/dashboard.html` — a self-contained, static reviewer queue (no server, no dependencies) built from the actual current pipeline output: a "needs your review" queue surfaced first, a "ready to send" queue below, and per-ticket detail showing the customer's message, the classify→draft→verify trail with the verifier's actual reasoning, and a plain-language "why this needs you" line for anything escalated. Open it directly: `open outputs/dashboard.html` (macOS) or just double-click it.

**Live preview (no cloning required)**: https://claude.ai/code/artifact/0d8d2c9a-d92d-4039-9062-12d3bd10afee — a snapshot of the dashboard as of the current commit. The committed `outputs/dashboard.html` file is the authoritative version; this link is a convenience.

**A note on that precision number**: my first full run measured escalation precision at a clean 1.00, but a second independent run measured 0.83 — one false positive on a feature-request ticket (T04). Rather than report whichever number looked better, I repeat-sampled the classifier directly (10 trials on the disputed ticket, 6 on a true-positive control), found ~90% accuracy on that specific boundary case, tried a couple of fixes, and eventually root-caused it: the *verifier* had equal, independent authority to re-derive the same ambiguous escalation rule as the classifier and could reintroduce the error on its own. Narrowing the verifier's authority (Iteration 6) removed that duplicate failure path in a follow-up repeated-trial check. Full story with real before/after numbers: [`outputs/reliability_check.md`](outputs/reliability_check.md) and `CHANGELOG.md`.

## Hot take

**The sharpest finding in this project came from building a dashboard, not from running an evaluation.** For most of this project's development, up to 76% of the drafter's replies and 14% of the baseline's were literally malformed — `d['reply']` contained a JSON string like `'{"reply": "Hi, thanks...", "citations": [...]}'` instead of plain text, because every prompt both told the model in English to "respond with ONLY a JSON object" *and* used `--json-schema` for the same shape, two redundant structuring mechanisms that caused the model to nest its own self-formatted JSON inside the schema's field. The composite quality scores never flagged it — after fixing both prompts and re-running the full evaluation, the numbers came back numerically identical, because the LLM judge was only ever asked to rate grounding, policy, and tone, never "is this actually sendable text." Proved this precisely: scored the exact same bugged reply with the old judge prompt (`tone_quality: 5`, didn't notice) and a fixed one with an explicit `clean_format` check (`clean_format: false, tone_quality: 0`, caught it immediately, plus an invented KB claim the old judge had also missed). Same input, same model, two different verdicts, because only one of them was asked the right question. **An LLM-as-judge and a human-facing view of the same output validate genuinely different things, and a defect can live entirely in the gap between them for as long as nobody looks at the second one** — this was only found because "the End to End Quality feedback was raw JSON" led to building `outputs/dashboard.html`, and finally *looking* at a reply the way a human would. Full evidence: `CHANGELOG.md` Iteration 7 and `TRAJECTORIES.md` section 6.

The humbling part is Iteration 8: after that fix, I republished the dashboard and moved on — and a human reviewer looking at the same screenshots caught two things I hadn't, a citations block leaking into customer-facing text and inconsistent greeting/sign-off formatting. Building the human-facing surface didn't fix my blind spot, it relocated it — I still needed someone else's scrutiny to find the next defect underneath the one I'd already found. See `CHANGELOG.md` Iteration 8 for the full fix and the fifth lesson it produced.

A single agent asked to both classify *and* draft in one pass didn't get worse at writing replies (its quality score was statistically the same as the final pipeline) — it got worse at applying a **compound policy rule**. The escalation rule is "flag if X (refund/fraud/discount) **or** Y (KB doesn't cover it)," and under the merged prompt that silently collapsed to just "Y," misfiring on an ordinary feature-request ticket. A dedicated classifier, doing nothing else, kept the full rule intact far more often.

But "far more often" is the honest phrase, not "always": that same dedicated classifier still misfires on the identical ticket about 1 time in 10, something I only found because a second independent run disagreed with the first and I bothered to repeat-sample instead of trusting either single run. Self-consistency majority voting, the obvious fix, barely helped (9/10 either way) at 3x the cost. The real lesson isn't "add a classifier" or "add more sampling" — it's that **a single eval run cannot distinguish a reliable design from a lucky draw**, and once you've found a residual error you can't cheaply eliminate, the better engineering move is making sure that error is safe (over-escalating to a human) rather than chasing the last few percent of determinism out of an inherently stochastic model.

I then tried a more targeted fix — a confidence field on the classifier, escalating whenever it reported low confidence — and it was a **clean null result**: every wrong trial was already a confident flip, not a hesitant answer, so the safety net had nothing to catch. That failure led somewhere more useful: a fresh false positive turned out to come from the *verifier*, not the classifier, independently re-deriving the exact same ambiguous escalation rule I thought I'd already fixed — because I'd stated that rule in two separate prompts, and either one could get it wrong on its own. Narrowing the verifier's authority (it no longer re-judges topic-sensitivity, only checks the draft against new evidence) removed that duplicate failure path in a follow-up test. **The generalizable version: before reaching for a fancier sampling or confidence-scoring fix, check whether you've stated the same policy logic in more than one prompt — duplicated authority over an ambiguous judgment call is a different failure mode than "the model is sometimes wrong," and hardening one copy does nothing to protect you from the other.** See `CHANGELOG.md` and `outputs/reliability_check.md` for the full before/after evidence on all three findings.
